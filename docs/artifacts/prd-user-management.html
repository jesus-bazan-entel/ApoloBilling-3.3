01

Resumen ejecutivo

Hoy el sistema distingue en la práctica solo dos niveles: superadmin (ve todo) y todos los demás (ven un subconjunto fijo, hardcodeado por ruta en el frontend). No existe forma de que el cliente administre el acceso de su propio personal.

Este documento define un modelo de tres roles con significado real de negocio, y un catálogo de módulos que Superadmin y Admin pueden asignar individualmente a cada usuario "normal", sin tocar código.

02

Contexto actual

Verificado directamente en el repo:

  • UserRole ya es Operator | Admin | Superadmin, con level() y can_manage() implementados por jerarquía — reutilizable tal cual.
  • main.rs registra casi todas las rutas de administración como superadmin only. No existe distinción real de "admin".
  • Layout.tsx filtra el menú con un único booleano adminOnly comparado contra role === 'superadmin'. App.tsx protege rutas con requiredRole="superadmin" hardcodeado.
  • No existe ninguna tabla de catálogo de módulos ni de permisos granulares.
Problema central

operator no tiene hoy ningún propósito de negocio distinto de "no-admin", y no hay manera de que el cliente autogestione qué ve su propio personal sin pedirle un cambio de código a Jesus.

03

Objetivos y alcance

  1. Redefinir los tres roles con semántica de negocio clara.
  2. Que Superadmin y Admin habiliten o deshabiliten, por usuario, qué módulos ve un usuario "normal".
  3. Que la restricción sea real — aplicada en el servidor, no solo ocultando un botón.
  4. Migrar usuarios existentes sin dejar a nadie fuera el día del corte.
  5. Dejar trazabilidad en auditoría de cada cambio de acceso.

Fuera de alcance

  • Permisos por acción (crear/editar/eliminar) dentro de un módulo.
  • Multi-tenancy real (varias empresas cliente aisladas en la misma instancia).
  • Jerarquía o "propiedad" entre distintos Admin sobre distintos Usuarios.
  • Cambios a la infraestructura de FreeSWITCH/Kamailio en sí.

05

Catálogo de módulos

Cada módulo tiene una clave estable (module_key), un nombre visible, una sección de menú y un min_role: el rol mínimo que accede sin necesidad de permiso explícito.

  • min_role = usuario → visible para Admin/Superadmin siempre; para Usuario solo si tiene el permiso explícito.
  • min_role = admin → visible para Admin/Superadmin; nunca asignable a Usuario.
  • min_role = superadmin → exclusivo de fábrica; nunca asignable a Admin ni a Usuario.

06

Modelo de datos

6.1 — Renombrar operator → usuario

-- 015_rename_role_operator_to_usuario.sql
BEGIN;

ALTER TABLE usuarios DROP CONSTRAINT IF EXISTS usuarios_role_check;
ALTER TABLE usuarios ADD CONSTRAINT usuarios_role_check
    CHECK (role IN ('usuario', 'admin', 'superadmin', 'operator')); -- alias temporal

UPDATE usuarios SET role = 'usuario' WHERE role = 'operator';

COMMIT;

En Rust, UserRole::Operator se renombra a UserRole::Usuario (serde rename = "usuario"). from_str() acepta temporalmente ambos strings como alias durante el corte.

6.2 — Catálogo de módulos

-- 016_module_catalog.sql
CREATE TABLE system_modules (
    id SERIAL PRIMARY KEY,
    module_key VARCHAR(50) UNIQUE NOT NULL,
    nombre VARCHAR(100) NOT NULL,
    seccion VARCHAR(50) NOT NULL,
    min_role VARCHAR(20) NOT NULL DEFAULT 'usuario'
        CHECK (min_role IN ('usuario', 'admin', 'superadmin')),
    always_visible BOOLEAN NOT NULL DEFAULT false,
    orden INTEGER NOT NULL DEFAULT 0,
    activo BOOLEAN NOT NULL DEFAULT true
);
-- + seed de las 20 filas de la sección 05

6.3 — Permisos por usuario

-- 017_usuario_modulos.sql
CREATE TABLE usuario_modulos (
    id SERIAL PRIMARY KEY,
    usuario_id INTEGER NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,
    module_key VARCHAR(50) NOT NULL REFERENCES system_modules(module_key) ON DELETE CASCADE,
    otorgado_por INTEGER REFERENCES usuarios(id),
    otorgado_en TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (usuario_id, module_key)
);
CREATE INDEX idx_usuario_modulos_usuario ON usuario_modulos(usuario_id);

Solo tiene sentido para cuentas con role = 'usuario'. Para admin/superadmin el acceso se calcula en código a partir del rol — evita duplicar datos y evita que una fila desincronizada rompa el acceso de un admin.

07

Reglas de negocio

Todo aplicado en el servidor — no solo en la UI.

7.1 — Módulos efectivos de una sesión

  • Si role ∈ {admin, superadmin}: módulos efectivos = todos los system_modules con min_role ≤ role.
  • Si role = usuario: módulos efectivos = {dashboard} ∪ usuario_modulos del usuario, filtrado a min_role = usuario y activo = true.

7.2 — Gestión de cuentas

  • Guard de ruta pasa de SuperadminUser a AdminUser.
  • Dentro del handler: current_user.role.can_manage(&target.role) antes de editar/eliminar. Un Admin que edita a otro Admin recibe 403.
  • Al crear un usuario, el rol solicitado se valida contra lo que el creador puede otorgar: Admin solo usuario; Superadmin, cualquiera.

7.3 — Gestión de módulos

  • Solo Admin/Superadmin.
  • target_user.role debe ser usuario — si no, 400.
  • Los module_key enviados deben existir y tener min_role = usuario — no se puede otorgar un módulo de fábrica burlando el catálogo.
08

Cambios de backend (Rust)

apolo-core

  • Renombrar UserRole::Operator → UserRole::Usuario (alias de parseo "operator").
  • Nuevos modelos: SystemModule, ModuleGrant.
  • UserRole::effective_modules(&self, grants, catalog) — centraliza la regla 7.1.

apolo-auth

  • Nuevo extractor ModuleAccess<"cdr">, análogo a AdminUser/SuperadminUser, que lee la lista de módulos embebida en el JWT.
  • Claims suma modules: Vec<String>, calculado en el login — sin consulta a DB por request.
Trade-off aceptado

Si a un Usuario logueado le quitan un módulo, el cambio tarda hasta JWT_EXPIRATION_SECS (30 min hoy) en aplicarse — salvo que el Admin fuerce su cierre de sesión desde Usuarios.

apolo-api

  • GET /api/v1/modules — catálogo completo (Admin+).
  • GET /api/v1/users/{id}/modules — módulos otorgados (Admin+).
  • PUT /api/v1/users/{id}/modules — reemplaza el set completo (Admin+, reglas 7.3).
  • Handlers de /users/* existentes: guard SuperadminUser → AdminUser + can_manage().
  • GET /auth/me suma "modules": [...].
  • Auditoría: user_created, user_role_changed, module_grant_updated, user_force_logout.
09

Cambios de frontend (React)

  • types/index.ts — UserRole pasa a 'usuario' | 'admin' | 'superadmin'; CurrentUser suma modules: string[].
  • App.tsx — requiredRole="superadmin" se reemplaza por requiredModule="carriers" usando las mismas claves del catálogo backend.
  • Layout.tsx — el filtro de menú deja el booleano adminOnly y pasa a comprobar si moduleKey está en los módulos efectivos de currentUser.
  • Users.tsx — selector de rol restringido por quién crea; nueva pestaña "Módulos visibles" (checklist por sección) con botón "Guardar módulos"; acción "Cerrar sesión del usuario".
Importante

Ocultar el ítem del menú es solo UX. La seguridad real la da el guard de módulo en el backend — nunca confiar solo en el ocultamiento del menú.

10

Migración de datos existentes

Riesgo principal

Hoy cualquier cuenta operator ya ve Dashboard, Llamadas, CDR, Cuentas, Planes, Saldos, Zonas y Tarifas. Migrarlas a usuario con cero módulos otorgados las deja solo con Dashboard el día del corte — incidente de soporte garantizado.

Mitigación obligatoria: otorgar automáticamente, al migrar, el mismo set de módulos que ya tenían:

INSERT INTO usuario_modulos (usuario_id, module_key, otorgado_por)
SELECT u.id, m.module_key, NULL
FROM usuarios u
CROSS JOIN system_modules m
WHERE u.role = 'usuario'
  AND m.module_key IN ('dashboard','active_calls','cdr','accounts',
                        'plans','balance','zones','rates')
ON CONFLICT DO NOTHING;

A partir de ahí, Admin/Superadmin ajustan por usuario según corresponda.

12

Criterios de aceptación

  • Un Superadmin puede crear un Admin; un Admin no puede crear otro Admin ni un Superadmin (403).
  • Un Admin puede crear un Usuario y elegir qué módulos ve.
  • Un Usuario sin módulos otorgados solo ve el Dashboard al iniciar sesión.
  • Acceso por URL directa a un módulo no otorgado responde 403 en el backend.
  • Forzar cierre de sesión aplica el cambio de módulos de inmediato.
  • dialplan, legacy_routing y system_settings nunca son asignables, ni para Admin.
  • Las cuentas operator existentes conservan su acceso actual tras la migración.
  • Cada cambio de módulo o de rol queda registrado en audit_logs.
