# Media modes: normal, proxy, bypass-after-bridge, bypass

The biggest capacity lever after "no transcoding". Read this before recommending
any media-mode change; each mode trades features for capacity, and the risks live
at the edges of the call chain (SBC/Kamailio, RTPEngine, far ends), not in
FreeSWITCH itself.

## Contents
1. What each mode does (official definitions)
2. Capacity effect
3. Features lost
4. Compatibility checklist (what to verify in the user's system)
5. Test matrix before any canary

## 1. What each mode does

From the official docs (`docs/media/media-handling.mdx` in
`github.com/signalwire/freeswitch-docs`):

| Mode | Official wording (abridged) | Variable / param |
|---|---|---|
| Normal | FS terminates RTP on each leg and processes it | default |
| Proxy | "passes RTP packets between endpoints transparently without decoding the payload… still allocates RTP ports for both legs… Transcoding is not possible" | `proxy_media=true` / `inbound-proxy-media` |
| Bypass | "rewrites the SDP to direct the two endpoints to exchange RTP directly… RTP does not touch the FreeSWITCH host at all… The server handles signaling only" | `bypass_media=true` / `inbound-bypass-media` (alias `inbound-no-media`) |
| Bypass after bridge | FS handles media until answer, then re-INVITEs both legs to take itself out | `bypass_media_after_bridge=true` |

Other official facts: `inbound-bypass-media` implicitly enables
`inbound-late-negotiation`; if both `proxy_media` and `bypass_media` are set,
proxy wins; with bypass, early media already present is cleared before entering
bypass; the jitter buffer exists only in normal mode.

## 2. Capacity effect

| Mode | Relays in the media path | What still limits FS |
|---|---|---|
| Normal | FS (userland, timer-clocked) (+ RTPEngine if present) | CPU per packet, timer precision, RTP ports, max-sessions |
| Proxy | FS forwards without decoding, **no timer** (packets sent as they arrive) | ports, threads, max-sessions; CPU per packet small |
| Bypass after bridge | FS only while ringing | signalling, max-sessions; re-INVITE success |
| Bypass | none in FS | CPS (sofia loop) and max-sessions only |

If there is no transcoding, proxy's CPU gain is small — but it removes the
timer dependency, which is the fragile part on VMs. Measure it; don't dismiss it.

## 3. Features lost

| Feature | Proxy | Bypass |
|---|---|---|
| Transcoding | ✗ | ✗ |
| Recording / playback / IVR prompts | ✗ (playback or record hangs up the call) | ✗ |
| Hold music injection | ✗ | ✗ unless `media-option=resume-media-on-hold` |
| In-band DTMF detection | ✗ | ✗ |
| RFC 2833/4733 DTMF | passes end to end (no PT translation) | passes end to end (no PT translation) |
| ptime / payload-type translation between legs | ✗ | ✗ |
| Ringback generated by FS | ✗ (originate sets ringback_data = NULL in proxy modes, switch_ivr_originate.c ~999) | ✗ |
| Per-call media stats in CDR (MOS, loss) | partial/none | none |
| RTP inactivity timeout in FS | yes | **no** (FS sees no RTP) |

## 4. Compatibility checklist (verify, don't assume)

1. **Codec on both legs** — bypass needs a common codec (collector "MEDIA IN USE").
2. **telephone-event payload type per leg** — e.g. carrier side 97 vs PBX side
   101. Today FS translates; in proxy/bypass the SDP is negotiated end to end
   and both ends must agree. With bypass-after-bridge the re-INVITE asks a leg
   to switch PT mid-call. Mandatory test.
3. **ptime per leg** — must match (collector shows `ptime=`).
4. **In-dialog re-INVITE through the SBC** — if a Kamailio/RTPEngine sits in
   front, it must run `rtpengine_offer/answer` (or `rtpengine_manage`) on
   in-dialog INVITE/UPDATE with SDP (check the `loose_route`/`WITHINDLG` →
   `t_on_branch`/`t_on_reply` path). Otherwise audio is lost right after answer.
5. **RTPEngine latching** — with parallel ring in pure bypass, every B-leg gets
   the same RTPEngine address. If one leg sends early RTP, `port-latching` can
   latch to the wrong source → one-way audio when another leg answers. Bypass
   after bridge avoids this (FS anchors media until answer).
6. **NAT / reachability** — the official FAQ warns bypass probably won't work
   with NAT. Check every far end's media IP (collector `remote_media=`, SDP
   `c=` lines): is it a relay (SBC) or the device itself? Public or LAN? Can
   the relay that will now talk to it reach it?
7. **Dead-call cleanup** — RTPEngine's `timeout` frees its own resources but
   sends no BYE. Need SIP session timers (`enable-timer`/`session-timeout`) or
   dialog keepalives in the proxy, plus `rtp-timeout-sec` while FS is in the
   media path.
8. **Ringback** — with FS not generating it (ignore_early_media, no `ringback`),
   the caller hears what the carrier generates on a 180 without SDP. Confirm
   this is today's behaviour too before calling it a regression.
9. **Features in the dialplan** — grep the dialplan for `playback`,
   `record_session`, `conference`, `hold_music`, `send_early_media`/`pre_answer`.
10. **Kernel forwarding** — if RTPEngine is the remaining relay, confirm
    `xt_RTPENGINE` is loaded and `/proc/rtpengine/<table>/list` has streams
    counting packets; otherwise it falls back to userspace.

## 5. Test matrix before any canary

For each mode under test, on one low-volume route:
answer on primary leg · answer on parallel leg (app) · caller cancels while
ringing · callee busy/reject · both legs ring, second answers · DTMF both
directions (check PT) · hold/unhold · re-INVITE from carrier · call > rtp
timeout with silence · BYE from each side · CDR duration matches reality.

## 6. How to enable

- Per call (dialplan, before `bridge`): `<action application="set" data="proxy_media=true"/>`
  or `bypass_media=true` / `bypass_media_after_bridge=true`.
- Per profile: `inbound-proxy-media`, `inbound-bypass-media` (applies to every
  inbound call on that profile — too broad for a first test).
- Keep `inbound-late-negotiation=true` for proxy media in the dialplan.
